Speculative decoding is supposed to be close to free speed: a small draft model
guesses several tokens ahead, the big target model checks them all in one pass,
and you keep whichever prefix it agrees with. On this benchmark the best setting
got a real 58% speedup. The next setting up in the same sweep, on the same
hardware, was slower than not using a draft model at all.

- **A 0.6B draft model sped up an 8B target model's decode by 58% at its peak
  setting**, from 60.0 tok/s to 94.7 tok/s, on a code-generation prompt with
  `num_draft_tokens=2`.
- **Past that peak, more draft tokens made things worse, not better.** At
  `num_draft_tokens=4` the same prompt dropped to 51.8 tok/s, below the 60.0
  tok/s baseline with no draft model at all. At `num_draft_tokens=8` it was
  44.4 tok/s.
- **On open-ended text, speculative decoding never won.** Every
  `num_draft_tokens` setting tested (1, 2, 4, 8, 16) was slower than the 58.8
  tok/s baseline for a creative-writing prompt. The best speculative setting
  still lost by 16%.
- **Memory was not the bottleneck here.** Peak memory stayed within about 70 MB
  across every cell, structured or open-ended, draft model or none. Whatever is
  costing throughput past the peak, it is not unified memory pressure.

## The setup

| | |
| --- | --- |
| Machine | Apple M5 Pro, 48 GB unified memory |
| OS | macOS 26.5.2 |
| Libraries | `mlx` 0.32.1, `mlx-lm` 0.31.3 |
| Target model | `mlx-community/Qwen3-8B-4bit` |
| Draft model | `mlx-community/Qwen3-0.6B-4bit` (same tokenizer family, required by `mlx_lm`) |
| Sweep | `num_draft_tokens` in {1, 2, 4, 8, 16}, plus a no-draft baseline, on two prompt types |
| Gen length | 320 tokens per generation |
| Reps | 5 per cell, 1 warmup, medians reported |

Two prompt types, chosen to test whether predictability matters: a **structured**
prompt (write four small, well-specified Python functions) and an **open-ended**
prompt (write a short reflective piece with no fixed structure). The idea is
that a draft model should guess more of the next tokens correctly when the
continuation is more constrained, and the data backs that up.

## The numbers: structured prompt

| `num_draft_tokens` | tok/s (median) | vs. baseline | Draft acceptance rate |
| ---: | ---: | ---: | ---: |
| 0 (baseline) | 60.0 | | |
| 1 | 80.4 | +34% | 44.4% |
| 2 | **94.7** | **+58%** | 59.7% |
| 4 | 51.8 | -14% | 69.4% |
| 8 | 44.4 | -26% | 75.0% |
| 16 | 48.6 | -19% | 80.3% |

Two draft tokens per round is the sweet spot. Below it, the draft model is not
generating enough candidates per round to pay back the overhead of running a
second model at all. Above it, throughput falls even though the acceptance
rate keeps climbing, which is the counterintuitive part: the fraction of
emitted tokens that came from the draft model rises from 44.4% at
`num_draft_tokens=1` all the way to 80.3% at `num_draft_tokens=16`, and
throughput still gets worse, not better.

## The numbers: open-ended prompt

| `num_draft_tokens` | tok/s (median) | vs. baseline | Draft acceptance rate |
| ---: | ---: | ---: | ---: |
| 0 (baseline) | 58.8 | | |
| 1 | 49.4 | -16% | 35.9% |
| 2 | 46.0 | -22% | 49.7% |
| 4 | 38.3 | -35% | 54.1% |
| 8 | 39.6 | -33% | 60.3% |
| 16 | 25.2 | -57% | 61.3% |

No setting beats the baseline here, not even `num_draft_tokens=1`. Acceptance
rate is lower at every matched setting than the structured prompt's (35.9% vs.
44.4% at `num_draft_tokens=1`, 60.3% vs. 75.0% at `num_draft_tokens=8`), which
is what you would expect: a small draft model guesses correctly more often
when the target's next tokens are more constrained by syntax and convention,
less often when they are open-ended prose. Lower acceptance means more of the
draft model's guesses get thrown away, and every thrown-away guess is compute
spent for nothing.

## Why acceptance rate keeps rising while speed falls

This is the part that does not match the simple mental model of speculative
decoding as "free" speedup. In `mlx_lm`, each round works like this: the draft
model generates `num_draft_tokens` candidates one at a time (a sequential
chain of small forward passes through the 0.6B model), then the target model
verifies the whole candidate sequence in a single batched pass and accepts
whichever prefix matches what it would have generated on its own.

Two costs scale with `num_draft_tokens`, and only one of them shows up in the
acceptance-rate number. The draft model's forward passes are sequential and
their count grows linearly with `num_draft_tokens`, so the fixed latency per
round grows too, whether or not those extra guesses get accepted. The
acceptance rate reported above only counts what fraction of *emitted* tokens
came from an accepted draft guess, not how much draft compute was spent
generating candidates that got rejected partway through the round. A round
with `num_draft_tokens=16` where the target accepts the first 5 tokens still
paid for all 16 sequential draft forward passes before verification could
happen. As `num_draft_tokens` grows, the marginal accepted token gets more
expensive to produce even as the cumulative acceptance rate keeps climbing,
because a growing share of each round's draft compute is spent on candidates
past the point where the target would have diverged anyway.

Peak memory does not explain any of this. It sat between 5.12 GB and 5.19 GB
across every single cell in the sweep, a spread of about 70 MB, regardless of
prompt type, draft model presence, or `num_draft_tokens`. The 0.6B draft
model's own weights and KV cache add a rounding error to a machine with 48 GB
of unified memory. Whatever the cost of extra draft tokens is, it is wall-clock
latency from sequential small forward passes, not memory pressure. That
distinguishes this result from the batch-concurrency post in this series,
where the wall was unified memory running out. Here, the wall is the fixed
per-step overhead of running a second autoregressive model, compounding once
you ask it to run more steps per round than the target ends up needing.

## What this means in practice

If you are running `mlx_lm` with a small, well-matched draft model on
predictable, structured generation, code being the clearest example,
speculative decoding is a real win here: 58% faster decode at
`num_draft_tokens=2`. That is the number worth remembering, not a generic
"speculative decoding helps" claim.

Do not assume more draft tokens is more speedup. On this hardware and this
model pair, the throughput curve peaks early and falls fast: `num_draft_tokens=2`
was the best cell in the whole sweep, and every setting above it lost ground,
in one case going from a 34-58% win to a 14-26% loss without changing anything
except that one number. If you are tuning `num_draft_tokens` for a production
setup, sweep it on your own workload rather than picking a default and moving
on. The `mlx_lm` default of 3 sits between the two best structured settings
tested here, which is a reasonable place to start but not obviously optimal
for every workload.

Do not assume speculative decoding helps at all for open-ended generation.
Every setting tested was slower than plain decoding for the creative-writing
prompt. If your traffic is mostly open-ended chat or long-form writing rather
than code or other structured output, measure before you turn this on. It cost
throughput here, it did not add it.

## What I am confident of, and what I am not

**Confident:**

- Speculative decoding produced a real, repeatable speedup on the structured
  prompt at `num_draft_tokens=1` and `num_draft_tokens=2`, peaking at +58% over
  baseline. These cells had tight run-to-run variance (robust CV under 0.04).
- Speculative decoding was slower than baseline on the open-ended prompt at
  every `num_draft_tokens` setting tested, and the gap widened as
  `num_draft_tokens` increased.
- Peak memory did not meaningfully change across any cell in the sweep. This
  is a compute and scheduling story, not a memory story.

**Not confident:**

- Two cells are flagged noisy in the raw data: open-ended `num_draft_tokens=1`
  (robust coefficient of variation 0.161) and open-ended `num_draft_tokens=4`
  (robust CV 0.409, the noisiest cell in the whole dataset). Both still landed
  below baseline across their runs, so the direction of the finding holds, but
  treat their exact tok/s figures as approximate rather than precise.
- One model pair, one machine, one chip. A different draft-to-target size
  ratio, a different model family, or a machine with a different core mix
  could shift where the peak sits. The shape I would expect to generalize is
  the existence of a peak followed by a falloff, not the specific
  `num_draft_tokens=2` number.
- Two prompt types is not a systematic sweep of predictability. It shows the
  direction (more constrained text accepts more draft tokens) but not where
  the acceptance rate stops helping for prompt types in between code and open
  prose.

## Reproducing this

```bash
python3 scripts/benchmarks/exp5_speculative_decoding.py \
    --target-model mlx-community/Qwen3-8B-4bit \
    --draft-model mlx-community/Qwen3-0.6B-4bit \
    --draft-tokens 1,2,4,8,16 --reps 5 --warmup 1
```

Run it plugged into AC power. Apple Silicon throttles differently on battery,
and every number in this post was captured on AC.
